# События

![Бости приветствует звенящий колокольчик](../assets/mascot/bostie-events.webp){ align=right width="180" loading=lazy }

Discord сообщает боту о происходящем через события шлюза: отправлено сообщение, присоединился участник, изменилась роль. Слушатель — это асинхронная функция, которая принимает одно событие.

`@bot.listen` читает аннотацию типа первого параметра и регистрирует функцию для этого класса события или для каждого класса из объединения. `@bot.listen(MessageUpdate)` вместо этого явно называет классы — для функции без аннотации или с более широкой аннотацией. Классы находятся в `bostie.events`, а [список событий](../reference/event-list.md) называет каждый из них с его интентами и полями. У [роутера](routers.md) есть такой же декоратор.

Каждый слушатель выполняется как отдельная задача, поэтому медленный слушатель не задерживает ни остальных, ни следующее событие. Задача запускается сразу: код слушателя до первого `await` выполняется до обработки следующего события. Исключение — слушатели `Starting` и `Stopped`: `start()` и `close()` дожидаются их по очереди. `bot.remove_listener(function)` снимает функцию со всех событий, которые она слушает.

## Только то, что вы слушаете { #only-what-you-listen-to }

bostie просит своё ядро на Rust пересылать только те имена диспетчеризации, которые что-то в боте использует: ваши слушатели, кэш, маршрутизация команд и компонентов и ожидающие вызовы ожидания. Все остальные события отбрасываются до того, как дойдут до Python, поэтому если ничего не слушать, это ничего не стоит. Типизированные события декодируются один раз на диспетчеризацию и только тогда, когда они кому-то нужны.

## Интенты { #intents }

Большинство событий Discord присылает только боту, который запросил их интенты. `Bot(intents=...)` по умолчанию равен `Intents.DEFAULT` — все интенты, кроме трёх привилегированных. Если слушатель регистрируется на событие, которое не доставляет ни один из интентов бота, bostie пишет в лог предупреждение с именем интента, который нужно добавить, и напоминает, что привилегированный интент нужно ещё и включить в Developer Portal. Подробнее о них — в разделе [«Интенты»](gateway.md#intents).

## Старые значения и кэш { #old-values-and-the-cache }

События обновления несут `old` — объект в том виде, в каком он был в [кэше](cache.md) до изменения, а события удаления несут удалённый объект: `RoleUpdate.old`, `ScheduledEventUpdate.old`, `MessageDelete.message`, `MemberRemove.member`. Они равны `None`, если объекта не было в кэше. Сообщения кэшируются только с `Bot(max_messages=...)`, участники — только с `members=True`, присутствие — только с `presences=True`.

`await bot.wait_for(Event, check=None)` возвращает следующее событие этого класса, для которого `check` возвращает истину. `async with bot.stream(Event, check=None) as events:` ставит в очередь каждое подходящее событие, пока выполняется блок, — для `async for`; события, пришедшие во время выполнения тела цикла, не теряются. Ни у того, ни у другого нет собственного тайм-аута, поэтому ограничивайте их с помощью `asyncio.timeout()`. Исключение, выброшенное `check`, выбрасывается из ожидания. `bot.wait_for_component` и `bot.wait_for_modal` делают то же самое для [использований компонентов](components.md#waiting-for-a-click-inside-a-handler) и [отправок модальных окон](modals.md#waiting-for-the-submit-inside-a-handler).

## Сырые события и события, которые bostie не моделирует { #raw-events-and-events-bostie-does-not-model }

```python
--8<-- "docs/snippets/events/custom_events.py"
```

`@bot.listen_raw("NAME", ...)` доставляет `RawEvent` для каждого указанного имени диспетчеризации, смоделированного или нет, а слушатель с аннотацией `RawEvent` получает все диспетчеризации. У `RawEvent` есть имя диспетчеризации `name`, её порядковый номер `seq` и полезная нагрузка в виде `raw` (каждый раз новый `dict`) или `raw_json` (байты). У каждого типизированного события тоже есть `raw` и `raw_json`.

Если Discord присылает полезную нагрузку, которая не подходит к своему классу, например без поля, которое документация называет обязательным, bostie один раз на имя события пишет предупреждение в лог, и типизированные слушатели пропускают это событие, а слушатели `RawEvent` по-прежнему его получают.

## Собственные события { #events-of-your-own }

Унаследуйтесь от `BotEvent` с `kw_only=True` и отправьте экземпляр через `bot.dispatch(event)`: его слушатели, ожидания и потоки получат его, как любое другое событие. Подкласс без `NAME` называется по своему модулю и классу. Классы событий — неизменяемые структуры `msgspec`, поэтому их поля объявляются аннотациями.

## События жизненного цикла и шардов { #lifecycle-and-shard-events }

bostie отправляет собственные события о боте: `Starting`, `Started`, `Stopping` и `Stopped` вокруг [жизненного цикла](running.md#the-lifecycle); `ShardReady`, `ShardDisconnect`, `ShardStop` и `ShardBackpressure` о каждом [шарде](sharding.md); `ListenerError` и `TaskError` о сбоях. Голосовые подключения отправляют [голосовые события](../voice/index.md#events) через тот же `@bot.listen`.

## Когда слушатель выбрасывает исключение { #when-a-listener-raises }

Исключение в слушателе отправляется как событие `ListenerError` с `listener`, `event` и `error`. Если слушателя `ListenerError` нет, bostie пишет исключение в лог с трассировкой; если он есть, логирование на вашей стороне. Исключение в слушателе `ListenerError` только пишется в лог.
