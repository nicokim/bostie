## Что он хранит { #what-it-keeps }

| Что хранится | По умолчанию | Параметр |
|---|---|---|
| серверы с их ролями, эмодзи и стикерами | да | |
| каналы и активные ветки | да | |
| голосовые состояния | да | |
| запланированные события, трибуны и звуки звуковой панели | да | |
| пользователь бота и его собственный участник на каждом сервере | да | |
| все участники | нет | `members=True`, нужен `Intents.GUILD_MEMBERS` |
| присутствие участников, которые не в статусе «Не в сети» | нет | `presences=True`, нужен `Intents.GUILD_PRESENCES` |
| последние сообщения | нет | `max_messages=N` |
| последние личные каналы | нет | `max_dm_channels=N` |

`Bot(cache=False)` ничего не хранит, и тогда остальные параметры вызывают `ValueError`. Параметр, для которого нет интента, вызывает `MissingIntent` при создании `Bot`. Каналы хранятся в том виде, в каком их прислал Discord, кроме полей, которые `CHANNEL_UPDATE` не поддерживает в актуальном состоянии (`last_message_id`, `message_count`, `member_count`, `last_pin_timestamp`): они равны `None`.

С `members=True` при подключении бота Discord присылает только часть участников больших серверов. Тогда bostie запрашивает остальных — по одному серверу за раз на шард, — и шард считается готовым только после того, как его серверы заполнены. `chunk_members=False` пропускает это, и кэш заполняется по мере того, как участники присоединяются, меняются или говорят. Запросы, упёршиеся в лимит, повторяются после задержки, указанной Discord.

## Поиск { #lookups }

| Метод | Возвращает |
|---|---|
| `guild(id)`, `guilds()` | один `Guild` или все |
| `channel(id)`, `guild_channels(guild_id)` | `Channel` или каналы сервера вместе с его активными ветками |
| `role(id)`, `guild_roles(guild_id)` | `Role` или роли сервера |
| `voice_state(guild_id, user_id)`, `guild_voice_states(guild_id)` | где пользователи находятся в голосе; `None`, если пользователь не в голосовом канале |
| `scheduled_event(id)`, `guild_scheduled_events(guild_id)` | `ScheduledEvent` или события сервера |
| `stage_instance(id)`, `guild_stage_instances(guild_id)` | идущую `StageInstance` или трибуны сервера |
| `soundboard_sound(sound_id)`, `guild_soundboard_sounds(guild_id)` | `SoundboardSound` или звуки сервера |
| `me(guild_id)` | собственный `Member` бота на сервере |
| `member(guild_id, user_id)`, `guild_members(guild_id)` | участников; только самого бота, если не задано `members=True` |
| `presence(guild_id, user_id)`, `guild_presences(guild_id)` | присутствие, с `presences=True`; `None`, если пользователь не в сети |
| `user(id)` | пользователя бота или пользователя участника либо личного канала из кэша |
| `dm_channel(user_id)` | личный канал бота с пользователем, если он хранится |
| `message(id)` | одно из последних `max_messages` сообщений |
| `permissions(channel_id, member=None)` | права участника в канале или права бота, если `member` не указан |
| `guild_permissions(guild_id, member=None)` | то же самое на уровне всего сервера |

Для того, чего нет в кэше, методы поиска возвращают `None` или пустой список. `bot.cache.clear()` очищает кэш. События обновления и удаления несут объект из кэша в состоянии до изменения, как объясняет раздел [«События»](events.md#old-values-and-the-cache).

`bot.lookup` возвращает объект из кэша, если он там есть, а иначе запрашивает его через REST: `user(user_id)`, `member(guild_id, user_id)`, `channel(channel_id)`, `guild(guild_id)`, `role(guild_id, role_id)` и `message(channel_id, message_id)`. То, что вернул REST, не сохраняется: кэш по-прежнему следует только за шлюзом, поэтому повторный поиск того же отсутствующего объекта снова делает запрос. Ошибки REST пробрасываются дальше, например `NotFound` для несуществующего ID.

## Запуск { #startup }

Шард готов, когда каждый сервер, перечисленный в его `READY`, пришёл как `GuildCreate`, или когда ни один сервер не приходил `guild_ready_timeout` секунд (по умолчанию 2). `Started` ждёт все шарды. `GuildCreate` с `joined=True` — это сервер, на который бота только что добавили; остальные — серверы, которые становятся доступными.

`large_threshold` — от 50 до 250, по умолчанию 50 — число участников, выше которого Discord присылает сервер без участников не в сети.

## Права { #permissions }

`cache.permissions(channel_id, member)` применяет правила Discord: у владельца сервера и администраторов есть всё; иначе учитываются роль `@everyone`, затем роли участника, затем переопределения канала для `@everyone`, ролей и участника; участник в тайм-ауте сохраняет только «Просматривать канал» и «Читать историю сообщений»; без «Просматривать канал» нет ничего; без «Отправлять сообщения» пропадают права, которые от него зависят; в голосовом канале без «Подключаться» пропадают голосовые права. Ветка использует переопределения своего родительского канала. Метод возвращает `None`, если в кэше нет канала, сервера или родителя ветки.

То же вычисление доступно и без кэша: `bostie.permissions.compute_permissions(guild, member, channel=None, *, parent=None)`, где `parent` — родительский канал ветки. В этом же модуле есть наборы `Permissions`, взятые из документации Discord: `ALL`, `NONE`, `TEXT`, `VOICE` и `STAGE` (права, которые применяются к каждому виду канала), `ELEVATED` (те, что требуют двухфакторной аутентификации в аккаунте модератора, если её требует сервер) и `TIMED_OUT` (те, что сохраняет участник в тайм-ауте).

Внутри взаимодействия кэш не нужен: `ctx.interaction.app_permissions` хранит права бота в канале, а `ctx.member.permissions` — права пользователя.

## Иерархия ролей { #role-hierarchy }

Участник может выгнать, забанить, отправить в тайм-аут или изменить только тех участников, чья высшая роль ниже его собственной, а Discord показывает имя участника цветом его высшей цветной роли. В `bostie.permissions` есть три вспомогательные функции, которые принимают `Guild` и участников из кэша, взаимодействия или REST:

| Функция | Возвращает |
|---|---|
| `top_role(guild, member)` | высшую `Role` участника или `None`, если у него есть только `@everyone` |
| `display_colors(guild, member)` | `RoleColors` его высшей роли с цветом или `None` |
| `can_act_on(guild, actor, target)` | стоит ли `actor` выше `target` — участника или роли: владелец выше всех, никто не выше владельца, а в остальных случаях высшая роль `actor` сравнивается по позиции с высшей ролью цели или с самой ролью, как это делает Discord при управлении ролями |

Роли на одной позиции упорядочиваются по ID — сначала более старая, — так же, как их упорядочивает Discord.
